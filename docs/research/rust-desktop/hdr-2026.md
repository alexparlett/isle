# HDR and colour management for Isle: research note (2026-11-02)

Scope: what P22 (B23) can build on today. Host: kernel 7.2.10, NVIDIA open
modules 615.78.08 on an RTX 5070 Ti (GB203), AMD iGPU beside it, Mesa
26.2.4, PipeWire 1.6.9, AOC U34G2G4R3 on DP-4 (3440x1440, modes to 144 Hz,
EDID max and max frame-average about 302 cd/m²).

"Local:" marks evidence gathered on this host today: the installed NVIDIA
README and changelog, `modetest`, and a small libdrm probe that sets
`DRM_CLIENT_CAP_PLANE_COLOR_PIPELINE` and walks each plane's colorops (read
only; it does not take DRM master). "Source:" marks code read at a named
revision through the GitHub API. Everything else carries a URL and a date.
*Unknown* marks what was not settled.

### 1.2 dividebysandwich/smithay `ds-hdr-master`

Source: GitHub API, 2026-11-02.

- Licence MIT (the repo's). Last push 2026-07-10. Base: upstream
  `efeb5976` of 2026-07-06; upstream master is 156 commits ahead of that
  base today, including changes to `drm/surface/atomic.rs`,
  `renderer/gles/mod.rs` and `wayland/mod.rs`, which the branch also edits.
- Three commits by dividebysandwich (2026-07-07), each co-authored with
  Drakulix because they carry #1143's code forward, then a merge of
  Christopher Snowhill's (losnoco) work (2026-07-09/10):
  1. `drm: support connector color state in atomic commits`:
     `ConnectorColorState` (Colorspace, `HDR_OUTPUT_METADATA`, max bpc)
     staged with `DrmSurface::use_color_state` and applied in the same
     atomic commit as mode, CRTC and planes; support probed via
     `supported_colorspaces`, `hdr_metadata_supported`, `max_bpc_range`;
     never emitted on page flips; `reset_connector` restores SDR; foreign
     HDR state read back on creation and resume. The message records that
     committing these properties on their own "hangs the display pipe on
     some drivers, notably nvidia". New `src/backend/drm/color.rs` (+371),
     `surface/atomic.rs` (+545).
  2. `wayland: add color-management and color-representation protocol
     support`: wp-color-management-v1 (parametric descriptions, surface
     feedback with change notifications) and wp-color-representation-v1.
     `src/wayland/color/management/mod.rs` (+1732). ICC was dropped
     (comment on #1143, 2026-07-04).
  3. `gles: renderer-level tex program override and solid color
     transform`: `GlesRenderer::set_default_tex_program_override` and
     `set_solid_color_transform`, so the compositor supplies the colour
     maths in its own shaders. Smithay does no colour maths itself.
  4. Snowhill's merge: protocol version 3, Windows BT.2100, Windows scRGB,
     `set_primaries`, extended target volume, `ext_linear` treated as HDR.
- No colorop (KMS colour pipeline) code, no Vulkan, no ICC.
  https://github.com/dividebysandwich/smithay/tree/ds-hdr-master

### 1.3 dividebysandwich/niri `hdr-smithay-master`

Source, 2026-11-02. Licence GPL-3.0. Last push 2026-07-10.

- Output HDR is per output, always-on or auto (fullscreen HDR client).
- Blend space: the framebuffer holds PQ/BT.2020 values and blending happens
  "directly in PQ-encoded space", which `blend.rs` calls an approximation.
  SDR content is decoded with a pure 2.2 power ("the piecewise sRGB curve
  would lift shadows"), converted BT.709→BT.2020, scaled to the reference
  luminance (default 203 cd/m², BT.2408) and PQ-encoded in every surface
  shader. PQ client content passes through numerically. Extended-linear
  content (scRGB, `ext_linear`) is mapped absolutely and "never tone
  mapped, only clamped". There is no tone mapping.
- Commit `4fe37a60` (2026-07-03): standalone connector commits "hung the
  nvidia driver (it treats a Colorspace change as a full modeset and wedges
  on incomplete pipeline state) -- confirmed also at 8-bit". It clamps
  client mastering data to the EDID and falls back to EDID desired values.
- Commit `8d2ecca6` (2026-07-09): Cyberpunk 2077 under vkd3d-proton only
  offered scRGB once niri advertised `ext_linear`, because Mesa's WSI
  exposes `VK_COLOR_SPACE_EXTENDED_SRGB_LINEAR_EXT` only when the compositor
  advertises sRGB primaries, `ext_linear` and `extended_target_volume`;
  winewayland maps scRGB swapchains to `create_windows_scrgb`.
- Commit `d9027797` (2026-07-09): HDR surfaces are converted to SDR for
  screencopy and screencast, using each output's reference luminance.
- A comment on #1143 (poelzi, 2026-08-21) reports HDR on NVIDIA with MSI
  and Dell monitors; the GPU model is not stated.
  https://github.com/dividebysandwich/niri/tree/hdr-smithay-master

## 3 Kernel colour pipeline and connector properties

### 3.1 The API

- Merged in Linux 6.19 (tagged 2026-02-08). `DRM_CLIENT_CAP_PLANE_COLOR_PIPELINE`
  is 7; it needs `DRM_CLIENT_CAP_ATOMIC`; with it set, the kernel rejects
  `COLOR_ENCODING` and `COLOR_RANGE`. Each plane gets an enum
  `COLOR_PIPELINE` whose values are the first colorop of each pipeline (0 is
  bypass); colorops chain by `NEXT`; `BYPASS` is optional per colorop.
  Source: `include/uapi/drm/drm.h`, `drm_mode.h`, `include/drm/drm_colorop.h`
  at torvalds/linux master 2026-11-01; https://docs.kernel.org/gpu/rfc/color_pipeline.html
- Colorop types: `1D Curve`, `1D LUT` (`drm_color_lut32`, `SIZE`,
  interpolation), `3x4 Matrix` (S31.32), `Multiplier` (S31.32), `3D LUT`
  (`SIZE` per edge, e.g. 17), and `Fixed Matrix` (preset YCbCr→RGB),
  added 2026-08-27 and first in v7.4-rc1, not in 7.3.
- Named curves: sRGB EOTF and inverse, PQ 125 EOTF and inverse (10000 cd/m²
  maps to 125.0), BT.2020 inverse OETF and OETF, Gamma 2.2 and inverse
  (Gamma 2.2 added 2025-11-26; present in 6.19).
- Post-blend (CRTC) colour pipeline: patch series v3 posted 2025-12-23
  (`DRM_CLIENT_CAP_POST_BLEND_COLOR_PIPELINE`), not in mainline as of
  v7.4-rc1. https://lwn.net/Articles/1051800. KWin has an untested draft
  for it (!9300, 2026-05-29). The CRTC stage is still legacy
  `DEGAMMA_LUT`/`CTM`/`GAMMA_LUT` or vendor properties.
- Display Next Hackfest 2026: YCbCr colorops discussed and tested on amdgpu;
  a `color format` property and a proposed "min bpc"; a commit flag to reset
  KMS state when switching compositors.
  https://github.com/Zamundaaa/zamundaaa.github.io/blob/master/_posts/2026-06-24-display-next-hackfest.md
  (Xaver Hugl, 2026-06-24)

### 3.2 NVIDIA

- 610.43.02 (2026-05-26) added the plane colour pipeline; known issue:
  compositors that mishandle non-bypassable colorops can blank the screen
  "when enabling system HDR"; workaround `nvidia_drm color_pipeline=0`.
  Local: `/usr/share/doc/nvidia/NVIDIA_Changelog`, README "Wayland Known
  Issues". Local: `/sys/module/nvidia_drm/parameters/color_pipeline` is `Y`.
- Local probe (615.78.08, GB203, cap set): each plane offers `Bypass`,
  `NVIDIA Full`, `NVIDIA Lite`, `NVIDIA FP Full`, `NVIDIA FP Lite`.
  Source `kernel-open/nvidia-drm/nvidia-drm-color-pipeline.c` at tag
  615.78.08 matches:
  - Full: 3x4 (FMT) → 1D curve (PQ 125 EOTF only) → 1D LUT (1024) →
    multiplier → 3x4 (LMS) → **PQ 125 inverse EOTF, not bypassable** →
    3x4 (LMS→ITP) → 1D LUT (TMO, present on this GPU) → 3x4 (ITP→LMS) →
    **PQ 125 EOTF, not bypassable** → 3x4 (BLEND).
  - Lite: 3x4 → 1D curve (PQ 125 EOTF) → 1D LUT (1024) → multiplier → 3x4,
    all bypassable.
  - FP Full and FP Lite are the same without the degamma curve, LUT and
    multiplier (for float framebuffers).
  - The only named degamma curve is PQ 125 EOTF. No sRGB or Gamma 2.2
    curve: an SDR plane needs the 1024-entry 1D LUT. For comparison, the
    AMD iGPU on this host (card1) offers sRGB, PQ 125, BT.2020 and Gamma 2.2.
  - Every pipeline ends in linear light before blending (the Full chain
    decodes PQ again at the end; Lite decodes with its first curve). The
    encode for the wire is the CRTC's job: legacy `GAMMA_LUT` (1024
    entries) or vendor `NV_CRTC_REGAMMA_TF` (Default, Linear, PQ),
    `NV_CRTC_REGAMMA_LUT` (1024), `NV_CRTC_REGAMMA_DIVISOR`. The vendor
    `NV_PLANE_*` properties are still exposed beside the colorops.
- KWin and NVIDIA: KWin bug 520842 (filed 2026-05-30, 610.43.02, RTX 4070
  and RTX 5070 Ti among reporters): crash in `DrmLutColorOp32::program()`;
  fixed in 6.7.1 by checking every colorop for bypass ("There can be
  non-bypassable colorops after the last one we use"). KWin disabled colour
  pipelines on NVIDIA for 6.7 (!9426, 2026-06-19), on AMD too (!9436,
  2026-06-21), by default in 6.6 (!9607, 2026-07-20) and in 6.8 (!10079,
  2026-10-12, "efficiency is less important than visible color problems").
  `KWIN_DRM_USE_COLOR_PIPELINE=0|1` overrides (!9001).
  https://bugs.kde.org/show_bug.cgi?id=520842,
  https://invent.kde.org/plasma/kwin/-/merge_requests/9426,
  https://invent.kde.org/plasma/kwin/-/merge_requests/10079
- KWin bug 526998 (2026-10): HDR prevents direct scan-out on NVIDIA; Hugl:
  "Because of hardware limitations and our requirement to do blending in
  non-linear space, direct scanout with color transformations only works on
  current Nvidia (and Intel) hardware if there's only a single plane".
  http://www.mail-archive.com/kde-bugs-dist@kde.org/msg1221240.html
- Mutter does not set the colour-pipeline cap (main, 2026-10-28). Source:
  `src/backends/native/meta-kms-impl-device.c`.

### 3.3 Connector properties on this host

- Local `modetest -M nvidia-drm -c`: DP-4 has `Colorspace` (Default,
  BT2020_RGB, BT2020_YCC), `HDR_OUTPUT_METADATA` (blob, empty), a vendor
  `dithering mode` (auto, off, static 2x2, dynamic 2x2, temporal, on),
  `vrr_capable`. **There is no `max bpc` property**, so the compositor
  cannot ask for 10 bpc on the wire; the driver chooses.
- NVIDIA added `HDR_OUTPUT_METADATA` and `Colorspace` in 545 (2023-10-17);
  in 565 it changed the fallback for limited bandwidth from 10 bpc YCbCr
  4:2:2 to 8 bpc RGB with dithering. Local changelog.
- Bandwidth (calculation): the 144 Hz mode has a 772.42 MHz pixel clock;
  RGB at 10 bpc is 23.2 Gbit/s, under DP 1.4 HBR3's 25.92 Gbit/s payload, so
  10 bpc at 144 Hz should not need DSC if the link trains at HBR3. Whether
  it does, and what bpc the driver actually sends, is *unknown*.

### 3.4 Planes and formats on this host

Local libdrm probe of card2, 2026-11-02, read only (not master; the
running compositor held it). Raw output kept outside the repository.

- **Planes per CRTC:** one primary, one overlay and one cursor; each can be
  on only its own CRTC. CRTC 205 drives DP-4 at 3440x1440@144.
- **Primary and overlay formats** (23):
  - 10-bit only in ABGR order: `XB30` and `AB30`. There is no `XR30`/`AR30`.
  - FP16 only as `XB4H` and `AB4H`.
  - `AB48` (16-bit UNORM), and the YUV formats `P010`, `P012`, `P210`.
  - Seven modifiers each: LINEAR and block-linear heights 0–5, none
    compressed.
- **Cursor plane:** `AR24` with LINEAR only. It has no `COLOR_PIPELINE` and
  no vendor colour properties.
- **What the planes lack:** `zpos`, `COLOR_ENCODING` and `COLOR_RANGE` are
  absent on every plane. Only overlays have `alpha` and `pixel blend mode`.
- **The session's state at the probe:**
  - every plane's `COLOR_PIPELINE` was Bypass;
  - `Colorspace` was Default and `HDR_OUTPUT_METADATA` was unset;
  - `GAMMA_LUT` was an exact identity of 1024 entries (night light off);
  - `VRR_ENABLED` was 0;
  - the primary plane scanned out `AR24` block-linear.
- **Vendor properties beside the colorops:**
  - on the CRTC: `NV_CRTC_REGAMMA_TF` (Default, Linear, PQ),
    `NV_CRTC_REGAMMA_LUT` (1024) and `NV_CRTC_REGAMMA_DIVISOR`;
  - on each primary and overlay plane: `NV_INPUT_COLORSPACE` (None,
    scRGB Linear FP16, BT.2100 PQ), `NV_HDR_STATIC_METADATA`,
    `NV_PLANE_DEGAMMA_TF`, and LMS/ITP matrices and a tone-mapping LUT.
- **Kernel log:** no colour messages from nvidia-drm.

### 3.5 The spike (P22's 22.0)

`spikes/hdr-modeset`, `gl` mode, 2026-11-02, inside the running session on
`renderD129` (NVIDIA), through Smithay's `GlesRenderer`:
- **Extensions:** `GL_EXT_color_buffer_half_float`,
  `GL_EXT_color_buffer_float` and `GL_EXT_texture_norm16` are all present.
- **An `Abgr16161616f` texture as a render target** keeps values outside
  0–1 through a clear and a solid draw. It read back `(2.0, 0.5, -0.25)`
  and `(4.0, 1.0, -1.0)` exactly. P22's blend space (choice 10) holds.
- **GBM scan-out buffers as render targets:**
  - `AB30`, `XB30` and `AB4H` buffers allocated with
    `RENDERING | SCANOUT` bind and render with the renderer's
    block-linear modifiers.
  - An `AB30` clear of (0.5, 0.25, 1.0) read back as R 511, G 256, B 1023.
  - With the implicit modifier alone, binding failed for every format,
    `AR24` included in the first run. The compositor already passes the
    modifier list.
  - Smithay's `copy_framebuffer` cannot read `XB30`. That is the
    read-back's limit, not the target's.

`run` mode, 2026-11-02: the modeset, from a free console on the host with
the session logged in on its own console. It ran three times.
- **The modeset.** An atomic modeset with `Colorspace=BT2020_RGB`, the
  EDID's metadata and an `XB30` dumb buffer passes TEST_ONLY and commits
  in 200–290 ms. nvidia-drm logs "Infoframe changed on CRTC 0 (hdr=1
  colorspace=1 vsif=0)" on each switch. There was no hang in about twenty
  switches.
- **The monitor's answers** (third run, asked on screen):
  - it reports HDR in its menu; it shows no sign on the screen;
  - the bars up to 250 cd/m² are distinct, and 302 and up look alike,
    which is the EDID's peak;
  - BT.2020's primaries look deeper than BT.709's;
  - **203 cd/m² in HDR looks dimmer than SDR's white** in the monitor's
    SDR mode.
- **Screen off and on:**
  - SDR by `ACTIVE`, HDR by `ACTIVE`, and HDR disabled and relit (the way
    Isle sleeps a screen) all came back, lit, and in HDR where they had
    been.
  - **In the first run, HDR by `ACTIVE` stayed black.** It stayed black
    through a later SDR modeset, until the session took the card back and
    relit the screen. That run held the screen off for 5 s and waited 10 s
    after; the later runs held it off for 5 s and waited for the answer.
    It did not happen again. It is the 615 DisplayPort wake reports' shape
    (§9), and stays open.
- **Leaving HDR** (`--leave`, `--leave-unreset`). An output in HDR was
  disabled and the program exited, then the console was shown by
  switching to another one.
  - Resetting `Colorspace` and `HDR_OUTPUT_METADATA` in the disabling
    commit itself (CRTC_ID 0, ACTIVE 0, MODE_ID 0, planes off) commits in
    66 ms with no hang. The ported Smithay code's `reset_connector`
    already does this.
  - Without the reset, the console still looked normal **on this
    monitor**: PQ's full white clips at the panel's 302 cd/m², about its
    SDR white, so the test cannot show the difference here.
  - Exiting on the console's own VT leaves it black until a VT switch,
    HDR or not; fbcon redraws only on a switch.

## 4 How other compositors composite HDR

| | Blend space | SDR in HDR | Tone mapping | Offload |
|---|---|---|---|---|
| KWin 6.2+ | Gamma 2.2 encoding with 1.0 = the screen's max luminance, 10-bit buffer preferred over FP16 | SDR and HDR both mapped relative to the "SDR brightness" (reference) setting; PQ reference 203 | ICtCp intensity curve when content metadata exceeds the display (6.2) | Final gamma 2.2→linear→night light→PQ in the CRTC LUT, no full-screen pass; plane colorops implemented but off by default |
| Mutter 50/51 | For a PQ output: sRGB primaries, gamma 2.2, luminance scaled from reference (extended range) | Reference white 203 by default; luminance settings since 48 | ICtCp tone mapping (49); "Disable tone mapping with HDR" (50) | CRTC colour properties (50); no plane colorops |
| wlroots 0.20 / sway 1.12 | Vulkan renderer only: two-pass, linear `R16G16B16A16_SFLOAT` blend image, output pass encodes (sRGB, PQ, 3D LUT) | sRGB profile became piecewise sRGB; `gamma22` profile kept | *unknown* | Uses `Colorspace`, `HDR_OUTPUT_METADATA`, `max bpc`, `GAMMA_LUT`; no colorops |
| Hyprland 0.57 | Per-surface shader to the output's description; whether blending is linear was not established | `sdrbrightness`, `sdrsaturation` (default 1.0) | ICtCp (`tonemap.glsl`); ICC via a 3D LUT | *unknown* |
| gamescope (DRM) | Vulkan composite per layer with shaper and 3D LUTs | `--hdr-sdr-content-nits`, default 400; optional inverse tone mapping | Yes | AMD vendor plane properties (`AMD_PLANE_*`); no colorops |
| niri fork | PQ-encoded BT.2020 | Pure 2.2 decode, reference 203 | None | None |
| cosmic reference | 8-bit SDR intermediate, PQ conversion in a final 10-bit pass | Per-output reference white | *unknown* | Scan-out off while the pass runs |

Pitfalls seen across them:
- **Gamma 2.2 or piecewise sRGB for SDR.** wp-color-management v2
  deprecated the `srgb` transfer function as ambiguous and says "use
  gamma22 for video, motion picture and computer graphics". KWin, Mutter
  and the niri fork decode SDR with 2.2; sway 1.12 moved its default to
  piecewise. KWin's screenshot buffer is gamma 2.2 while Spectacle tags PNGs
  sRGB, so dark tones save too bright (bug 525876, 2026-10-15).
  http://www.mail-archive.com/kde-bugs-dist@kde.org/msg1219016.html
- **Banding.** Linear values in 8 or 10 bits band in the shadows (KWin part
  4). Low-resolution hardware LUTs band (KWin 525839, 526998).
- **Washed-out SDR.** Mutter fixed "desaturated SDR content in HDR mode"
  in 51.rc (!5230) and missing mastering metadata in 51.beta (!5199);
  jibsta210's cosmic shader was washed out (1.4).
- **Direct scan-out vs. transforms.** Every compositor here disables or
  limits scan-out when a plane needs a colour transform; NVIDIA hardware
  blends linear, so it fits only a single plane for compositors that blend
  non-linearly (3.2).
- **Cursor.** KWin: "direct scanout is expected not to work while the
  cursor is visible" in HDR (526998).

## 5 The protocols and their clients

### 5.1 wp_color_management_v1

Source: `staging/color-management/color-management-v1.xml` at
wayland-protocols main, 2026-11-02.
https://gitlab.freedesktop.org/wayland/wayland-protocols

- Current interface version 3. History: v1 in 1.41 (2025-02); v2 in 1.47
  (2025-12-15): `compound_power_2_4` TF, `absolute_no_adaptation` intent,
  `get_image_description`, `ready2`/`preferred_changed2`, deprecated `srgb`
  and `ext_srgb` TFs, and "A compositor must not advertise" deprecated
  names; v3 (Windows BT.2100, committed 2026-05-08) first in 1.49
  (2026-06-07). 1.50 (2026-10-29) only fixes typos.
- Only the perceptual rendering intent is mandatory. Everything else is an
  advertised feature: `icc_v2_v4`, `parametric`, `set_primaries`,
  `set_tf_power`, `set_luminances`, `set_mastering_display_primaries`,
  `extended_target_volume`, `windows_scrgb`, `windows_bt2100`.
- Named primaries: srgb, pal_m, pal, ntsc, generic_film, bt2020,
  cie1931_xyz, dci_p3, display_p3, adobe_rgb. Named TFs: bt1886, gamma22,
  gamma28, st240, ext_linear, log_100, log_316, xvycc, st2084_pq, st428,
  hlg, compound_power_2_4 (srgb, ext_srgb deprecated).
- Windows-scRGB and Windows-BT.2100 are for Windows content; their
  reference white is unknown and 203 cd/m² is suggested.
- wp_color_representation_v1 (version 1): alpha modes (premultiplied
  electrical, premultiplied optical, straight), coefficients (identity,
  bt709, fcc, bt601, smpte240, bt2020, bt2020_cl, ictcp), range, chroma
  location.

## 6 Night light with HDR

- KWin 6.3 (Hugl, 2025-01-07) changes the output colour space's white
  point and lets the colour-managed renderer adapt colours, instead of
  scaling channels in the gamma ramp, which shifted greens towards blue.
  With HDR the channel factors sit in the CRTC LUT between gamma 2.2
  decode and PQ encode (part 4).
  https://github.com/Zamundaaa/zamundaaa.github.io/blob/master/_posts/2025-01-07-fixing-night-light.md
- Mutter uses `GAMMA_LUT`; 51.rc added night light without `GAMMA_LUT`
  (!5205). How Mutter combines it with HDR is *unknown*.
- cosmic-comp: night light is open (#2059) and tied to the Vulkan renderer
  on the roadmap (1.4).
- Local: NVIDIA's CRTC has `DEGAMMA_LUT` (1024), `CTM`, `GAMMA_LUT`
  (1024) and the vendor regamma properties. With a PQ signal a channel
  scale in the gamma ramp becomes `PQ⁻¹(k·PQ(x))` per channel over 1024
  entries, which is where KWin hit LUT precision limits (525839).

## 7 HDR capture

- **Screenshot portal**: no colour information; issue #1646 ("Add color
  profile information to the screenshot portal") was converted to a
  discussion on 2025-09-02. `PickColor` returns sRGB.

- **Mutter 50** (HDR screen sharing, !4928): when the monitor is BT.2020/PQ

  `meta-stream-source-monitor.c` (2026-10-28).
- **KWin**: the screencast plugin lists only 8-bit formats (KDE Discuss,

  Screenshot data is gamma 2.2 (7 above, bug 525876). No HDR screenshot
  file format found in Spectacle.
- **GNOME Shell screenshots**: MR 4223 proposes 16-bit PNG with cICP

- **WebRTC**: fails on HDR10 PipeWire streams with an EnumFormat error

- **File formats**: PNG Third Edition (W3C Recommendation, 2025-06) has the

  AVIF and JPEG XL were not researched.
- **niri fork**: converts HDR to SDR for captures at the output's reference
  luminance (1.3).

## 8 Skia and Freya

- Isle today: Skia draws every shell surface on the compositor's EGL context
  into `RGBA8` textures with no colour space (`crates/isle-shell/src/lib.rs`,
  `ColorType::RGBA8888`, `None`; ARCHITECTURE.md "Shell").
- Skia can do more: `kRGBA_F16` surfaces, tagged colour spaces including
  linear sRGB, Rec.2020 primaries and named PQ and HLG transfer functions
  (`SkNamedTransferFn::kPQ` with a 203 cd/m² reference).
  Source: `include/core/SkColorSpace.h` at google/skia main (2026-11-02).
  Skia converts sources to the destination's colour space and treats
  untagged content as sRGB. https://skia.org/docs/user/color/
- What drawing into linear F16 changes is what KWin measured: linear
  blending makes translucency and anti-aliased edges look different from
  the sRGB-space result, and costs a float buffer (part 4). Every
  compositor in §4 treats ordinary SDR clients as 8-bit gamma 2.2 content
  placed at the reference white; none renders its own UI in HDR.
- NVIDIA 610.43.02 added FP16 EGL framebuffer configs for Wayland
  *clients*; inside the compositor, an FP16 FBO needs
  `EXT_color_buffer_half_float` (Hyprland checks it plus
  `ABGR16161616F`, `src/render/OpenGL.cpp`).
- Conclusion: render the shell as 8-bit sRGB (gamma 2.2) and let the
  compositor map it like any SDR surface. F16 or PQ in Skia is worth it only
  for shell content that is itself HDR: an HDR wallpaper, or Mission
  Control and switcher thumbnails of HDR windows. Those textures come from
  the compositor and need to be mapped to SDR, or kept in the blend space,
  before Skia draws them.

## What this means for Isle

1. **Base the work on the community Smithay code, kept small, not on
   upstream.** Upstream Smithay will not have colour management until its
   Vulkan renderer exists, and may never have it for GLES (1.1). Port the
   three Smithay pieces as a short patch series on Isle's fork: connector
   colour state staged in the modeset commit, wp-color-management v3 plus
   color-representation, and renderer hooks. Take them from `ds-hdr-master`
   (MIT, 2026-07, 156 upstream commits behind) and compare its connector
   code with franzjeger's (MIT Smithay side, TEST_ONLY consistency,
   validated on an RTX 5090 at 3440x1440). Keep the colour maths in Isle's
   own shaders, so it can move to the Vulkan renderer when that lands.
   niri and cosmic-comp code is GPL-3.0: read it, don't paste it.
2. **Blend in gamma 2.2, not in PQ and not in linear FP16.** Composite into
   a 10-bit buffer encoded as BT.2020 primaries with gamma 2.2, where 1.0
   is the panel's maximum (about 302 cd/m²), the way KWin does. SDR
   surfaces and the shell keep their look; there is no FP16 cost, and
   shadows don't band the way linear 10-bit does. Encode PQ in a final pass
   first. Moving that pass to the CRTC's `DEGAMMA_LUT`/`CTM`/`GAMMA_LUT`
   (1024 entries each) comes later, as an A/B test for banding.
3. **SDR reference white is a setting, defaulting to 203.** The panel has
   about 1.5x headroom over 203 cd/m², so HDR adds little and a
   brightness slider for SDR matters more. Tone-map with an ICtCp intensity
   curve only when content metadata exceeds the EDID maximum; clamp
   extended-linear content as the niri fork does.
4. **Don't depend on NVIDIA's plane colour pipeline.** It has no sRGB or
   gamma 2.2 curve, its Full pipelines contain non-bypassable PQ stages,
   it blends in linear while the final encode stays on legacy or vendor
   CRTC properties, and KWin ships it disabled on every driver. Isle does
   not set the cap today, so `color_pipeline=Y` does not affect it. The
   offload worth having is direct scan-out of a fullscreen HDR10 game onto
   an HDR10 output. That needs no transform at all, so the plane can use
   the Bypass pipeline or skip the cap. Draw the cursor into its plane
   already PQ-encoded so scan-out can survive a visible cursor.
5. **Advertise what gamescope and Mesa check for.** Perceptual intent;
   features `parametric`, `set_primaries`, `set_luminances`,
   `set_mastering_display_primaries`, `extended_target_volume`,
   `windows_scrgb`, `windows_bt2100`; TFs `gamma22`, `st2084_pq`,
   `ext_linear`, `bt1886`, `compound_power_2_4`; primaries `srgb`,
   `bt2020`, `display_p3`. Never the deprecated `srgb` TF. The output's
   preferred description is BT.2020/PQ with reference 203 and max target
   from the EDID (302), which passes gamescope's "max above reference" test.
   ICC can wait.
6. **Night light moves into the shader when HDR is on.** Adapt the white
   point in linear light during composition (KWin 6.3). Keep the current
   `GAMMA_LUT` path for SDR outputs only. `gamma.rs` writes the ramp outside
   `DrmCompositor`'s commits; on an HDR output that must not happen,
   because standalone colour commits are what hung NVIDIA in the niri fork.
7. **Capture defaults to SDR.** Screenshots, streams and the colour pick
   map HDR to SDR at the reference white (portal and OBS can't carry PQ).
   Optional extras: a 16-bit PNG with `cICP` (BT.2020/PQ) plus an ICC
   profile, and an opt-in 10-bit stream tagged BT2020/SMPTE2084 as Mutter
   does.
8. **The shell stays 8-bit sRGB in Skia** (§8). Thumbnails of HDR windows
   for Mission Control and the switcher are rendered by the compositor and
   mapped to SDR before Skia draws them.
9. **First tests on the host, in order:**
   1. One atomic modeset with `Colorspace=BT2020_RGB`, `HDR_OUTPUT_METADATA`
      (from the EDID: 302 max, 302 max frame-average, 0 min) and a 10-bit
      primary format (XR30/XB30). Confirm on the monitor's OSD; check for a
      hang. Then reset to SDR and hand over to the greeter (B140-B143
      greeter path), since KMS state carries across.
   2. The SDR desktop through the PQ path at reference 203, next to the
      same desktop in SDR mode: brightness, saturation, near-black.
   3. `vulkaninfo` surface formats and colour spaces for an NVIDIA Vulkan
      client under Isle.
   4. A fullscreen HDR10 client scanned out with no transform: cursor
      hidden, then visible.
   5. Nested `gamescope --hdr-enabled` with a Proton game, and
      proton-cachyos with `PROTON_ENABLE_WAYLAND=1 PROTON_ENABLE_HDR=1`.
   6. DPMS off and on with HDR active at 144 Hz (the 615 DP wake reports),
      and VT switches.
   7. Night light with HDR on.
   Keep `nvidia_drm color_pipeline=0` and a 610.57.04 rollback in mind
   when reading failures.
